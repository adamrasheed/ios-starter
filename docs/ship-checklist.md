# Ship checklist

Everything between "it works on my simulator" and "it is on the App Store."

A green CI build proves that the code compiles and the pure logic is correct. It proves nothing
about purchases, entitlements, sync, or whether the app is allowed on the store. Those are the
items below, and most of them can only be checked by hand.

It also proves nothing about whether the app **runs**. A full green suite, a green build and a
clean lint all sat happily on top of a version that terminated on 100% of first launches, because
nothing automated walks first-run UI. That was found by launching the app. See "Launch it" below,
and do it first.

## App-specific gates, before anything else

> **Fill this in for your app, and delete this quote block.**
>
> Every app has two or three things that matter more than the generic list, and they are the ones
> nobody thinks to check because they are not on a checklist anywhere. Put them here, above the
> boilerplate, so they are read first.
>
> These are the ones worth writing down:
>
> - Whatever the product's central claim depends on. If the app is a scorer, a solver or a grader,
>   the gate is that its output was checked against something derived independently of the code
>   that produces it.
> - Every generated resource in the bundle (a puzzle library, a scoring table, a seeded dataset),
>   and the fact that it must be built by **the commit being shipped**. A resource generated by an
>   older build can carry labels the shipped code disagrees with, silently.
> - Any product promise that is a deliberate design decision rather than a feature, so that a
>   future change has to argue with it. "No difficulty tier is ever behind the paywall." "The
>   alternate events are never gated." Write the check so it is stronger than reading the screens:
>   naming the file that would have to reference `Entitlements` and confirming it does not is a
>   better gate than a walkthrough.

## Launch it, on cleared state

Do this before anything else on this page, on an erased simulator or after deleting the app.

```sh
xcrun simctl erase <device>
```

- [ ] Walk first run: onboarding, permission prompts, first-run setup, the first real screen
- [ ] Do the core action, then relaunch and confirm the state survived
- [ ] Open every screen's **empty state**, especially a paid one
- [ ] Repeat in both the locked and unlocked entitlement states

The two states most likely to be broken are first run (because your simulator is always past it)
and empty states (because you always have data). Both are what a new user sees first.

## Before the first submission

### Identity

- [ ] `PRODUCT_BUNDLE_IDENTIFIER` in `project.yml` matches the App ID in the developer portal
- [ ] `DEVELOPMENT_TEAM` set
- [ ] `MARKETING_VERSION` **matches the version record in App Store Connect**. A mismatch is
      rejected at upload, not at review, which is a slow way to find out. The scaffold ships `0.1`
- [ ] `CURRENT_PROJECT_VERSION` set, and higher than any build already uploaded
- [ ] App icon present at 1024pt. A missing icon fails upload, not review, and always later than
      you would like. A placeholder is enough to unblock the first upload
- [ ] `AccentColor` is your brand colour, not the template's

### The paywall sells only what shipped

The gate that near-misses most often. App Review tests in-app purchases, so a mismatch here is a
guideline 2.3.1 rejection. Two shipped apps from this template hit it: one sold two features that
had no implementing code, the other sold two **free** features as Pro unlocks.

- [ ] For every perk in `PaywallCopy.perks`, grep `Features/` for the code that delivers it. The
      `evidence` field on each perk is where the answer is recorded
- [ ] For every perk, confirm the feature is actually **gated**. A free feature sold as an unlock
      is the same rejection from the other direction
- [ ] The claim is consistent across all five places it lives: `PaywallCopy`, the App Store
      description, the IAP description in App Store Connect, the release notes, and the support
      page
- [ ] `CLAUDE.md` separates shipped from planned, if it lists planned features at all

**The rule: a perk goes on the paywall in the same commit that ships the feature, never before.**

### The paywall is in the right place

- [ ] No paid screen shows a paywall over its own **empty state**. Show the empty state ungated and
      move the gate to the action that creates the first record
- [ ] A locked-feature list is not a wall of padlocks. Open the cheapest entries so the boundary is
      a rule a user can state rather than an arbitrary sample
- [ ] The gate sits at the moment of accumulated value, not at the tab bar

### The things Apple rejects for

- [ ] **Restore Purchases is visible and works.** Mandatory for non-consumables and a routine
      rejection. It is in Settings and on the paywall by default. Confirm neither got removed
- [ ] **Privacy policy and support URLs verified in a browser.** See below
- [ ] Privacy nutrition labels filled in App Store Connect, and honest about what the app collects
- [ ] No placeholder copy anywhere a reviewer can reach: "Lorem ipsum", "example.com", "TODO"
- [ ] Demo mode cannot be triggered by a user. Confirm nothing sets `DEMO_MODE` in a release build
- [ ] If the app has accounts: a working demo account in App Store Connect review notes
- [ ] Any permission prompt has a usage string that says *why*, in user language. "This app needs
      camera access" is a rejection; "Scan a receipt to add it to your log" is not

#### Verifying the legal URLs is a browser job

A 404 is the easy failure. The expensive one is a page that answers a machine and shows a reviewer
a login wall. Three cheaper checks were tried on a real app and **all three produced a false
pass**: a hosted-notes API returned full content for a page that was merely shared by link;
`curl` plus `grep` cannot work on a client-rendered page, where a nonexistent subdomain returns
byte-identical output to a published one; and a third endpoint returned content without
establishing publish state either way.

- [ ] Load each URL in a **fresh browser context with no session**, and wait for the page's own
      words to render
- [ ] The URLs compiled into `SettingsView` are the published ones, not the authoring links
- [ ] Follow every inline link **on** those pages. A support page linking to the privacy policy by
      its authoring URL sends the reviewer to the same wall

### Purchases: device pass required

The simulator's local `.storekit` file is a simulation. It does not exercise Apple's real
purchase flow, and the failures it hides are the expensive ones.

- [ ] Product created in App Store Connect with an id that **exactly** matches `StoreProduct.pro`
      and the `.storekit` file. A mismatch means the paywall shows no price and the buy button
      does nothing, with no error anywhere
- [ ] Paid Applications Agreement signed and banking + tax details complete. Without this, products
      never load, no matter how correct the code is
- [ ] Buy the unlock on a **real device** with a **sandbox Apple ID**
- [ ] Delete and reinstall the app, tap Restore, confirm the unlock comes back
- [ ] Confirm the entitlement appears on a second device signed into the same Apple ID
- [ ] Confirm `RootView` injects `StoreKitEntitlementProvider`, not the mock. Shipping the mock
      gives every user Pro for free and nothing in the build or test process will tell you
- [ ] Confirm the `.storekit` file is not in the shipped bundle. `project.yml` excludes it from the
      app target's glob and re-adds it with `buildPhase: none`; deleting that exclude ships it
- [ ] Buy, then immediately confirm the unlock survives a relaunch. A re-derivation already in
      flight when the purchase completes can land after it and overwrite the new state
- [ ] If anything long-lived runs behind the gate, confirm it **stops** when the entitlement goes
      away. Gating the entry point is not the same as stopping the work

### If iCloud sync is enabled

Read ADR-006 in the decision log first. All four of these are manual.

- [ ] Run on a device signed into iCloud and confirm the console shows no fallback to a local store
- [ ] Confirm data propagates device A → device B, and B → A
- [ ] Deploy the CloudKit schema from Development to **Production** in the CloudKit Console
- [ ] Confirm the Release build's entitlements carry `aps-environment: production`

### Quality

- [ ] `swiftlint --strict` clean
- [ ] Test suite green
- [ ] Run the macOS CI job once (`gh workflow run build-test.yml`) so the shipped commit has been
      built somewhere other than your machine
- [ ] Launch on a physical device and use the core flow start to finish
- [ ] Check the largest Dynamic Type size on the main screens. Text that truncates into
      unreadability is a common one-star complaint
- [ ] Check dark mode
- [ ] Airplane mode: does anything that fetches fail gracefully, or does it hang forever with a
      spinner?
- [ ] Any generated resource in the bundle was built by the commit being shipped

## Listing

- [ ] Screenshots regenerated from the current build, not last release's
- [ ] Regenerated by the **right harness**. If the repo has more than one capture script, one feeds
      the listing and the other does not. Name the authoritative one here:
      `______________________`
- [ ] Every caption's subject is actually visible in its screenshot. A row appended to the end of a
      list can sit below the fold where no capture can reach it without a scroll hook
- [ ] Name, subtitle and keyword field written deliberately. The keyword field is invisible to
      users and does most of the discovery work
- [ ] Description leads with what the user gets, not a feature list
- [ ] Age rating answered honestly
- [ ] Export compliance: `INFOPLIST_KEY_ITSAppUsesNonExemptEncryption` is `NO` in `project.yml`,
      which is correct if you use only HTTPS. If you added your own encryption, this changes
- [ ] No em dashes in user-facing strings or listing copy. `lint.yml` checks this

### The in-app purchase images follow different rules

Not the app screenshots, and not interchangeable with each other. Getting this wrong costs a
round trip per mistake.

| Image | Where | Size | Error if wrong |
|---|---|---|---|
| Review screenshot (required) | The IAP's App Review Information | **1242x2688** | "The dimensions of one or more screenshots are wrong." The field validates against an older device size list that excludes 6.9-inch, so a 1320x2868 capture is rejected |
| Promo image (optional) | The IAP, in offer-code redemption | **exactly 1024x1024** | "Your image must be 1024 x 1024 pixels" |
| App screenshots | Version page, 6.9-inch slot | **1320x2868** | 6.5-inch and 6.7-inch inherit from 6.9-inch automatically |

- [ ] IAP review screenshot recaptured from **this** build. It is what App Review looks at when it
      inspects the purchase, so a stale one can show perks the build no longer sells
- [ ] The rejected size is deleted, not kept next to the correct one. A folder with both is how the
      wrong file gets grabbed next release

The `appstore-listing` skill produces the metadata and framed screenshots.

## Release

- [ ] Version bumped and committed
- [ ] Tag the commit you actually shipped, so you can reproduce a user's bug against their build
- [ ] Archive and upload (see `docs/releasing.md` for the command-line path, which needs no Xcode
      GUI, no App Store Connect API key and no app-specific password)
- [ ] TestFlight it yourself first. Ad-hoc signing hides entitlement problems that only appear in a
      distribution build
- [ ] Submit
- [ ] After approval: `main` now represents a binary real people are running. Develop on branches

## After

- [ ] Confirm the live listing renders correctly on a device, not just in App Store Connect
- [ ] Buy the product once with a real account to confirm the production purchase path works
      end to end. Sandbox and production are different systems
- [ ] Watch crash reports for the first few days. The first 48 hours surface device and locale
      combinations you do not have
- [ ] Record anything discovered during this pass that the next release should not rediscover.
      `docs/releasing.md` is the place for signing, upload and asset-slot facts
